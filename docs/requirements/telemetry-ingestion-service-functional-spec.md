# Функциональное техническое задание (BRD / FRD)

**Документ:** `docs/requirements/telemetry-ingestion-service-functional-spec.md`
**Статус:** Approved for Development
**Сервис:** telemetry-ingestion-service (Поддомен: Telemetry Ingestion & Real-Time IoT)

## 1. Введение и Назначение Сервиса

### 1.1 Бизнес-контекст
Для обеспечения сквозного контроля доставки грузов транспортные средства, контейнеры и рефрижераторные установки оснащаются бортовыми контроллерами и датчиками. `telemetry-ingestion-service` является входной дверью (Ingestion Gateway) для всего входящего потока данных телеметрии. Сервис обеспечивает бесперебойную приемку потоков данных со всего мира 24/7.

### 1.2 Проблемы, которые решает сервис
*   **Разнородность бортового оборудования:** Поддержка работы с десятками производителей трекеров (Teltonika, Wialon, CalAmp) и стандартов передачи данных (HTTP, TCP, MQTT).
*   **Высокая асинхронная нагрузка (Highload):** Способность выдерживать пиковые всплески трафика (до 100,000 событий в секунду) без потери гео-точек.
*   **Фильтрация и очистка "шума":** Отсечение дубликатов точек, некорректных GPS-данных (GPS drift / битые координаты) до того, как они попадут в бизнес-логику системы.

## 2. Доменная модель и Сущности (Domain Entities)

Сервис оперирует нетяжелыми доменными сущностями, оптимизированными для работы в памяти:

```text
 ┌───────────────────────┐       1..N      ┌─────────────────────────┐
 │   TelemetryDevice     ├────────────────►│     TelemetryPoint      │
 └───────────────────────┘                 └────────────┬────────────┘
                                                        │ 1
                                                        │ 1..N
                                                        ▼
                                           ┌─────────────────────────┐
                                           │     SensorReadout       │
                                           └─────────────────────────┘
```

*   **TelemetryDevice (Устройство телеметрии):** Физический трекер или бортовой компьютер. Идентифицируется по уникальному IMEI / Hardware ID. Содержит привязку к транспортному средству или контейнеру.
*   **TelemetryPoint (Точка телеметрии):** Неизменяемый (Immutable) факт местоположения в конкретный момент времени. Атрибуты: `latitude`, `longitude`, `altitude`, `speed`, `heading`, `timestamp`, `gps_accuracy`.
*   **SensorReadout (Показание датчика):** Дополнительные показания, привязанные к гео-точке. Примеры: `temperature_celsius`, `humidity_percent`, `door_opened_status`, `fuel_level_liters`, `battery_level`.

## 3. Бизнес-логика и Жизненный Цикл

### 3.1 Конвейер обработки входящего пакета (Ingestion Lifecycle)

```text
 [RAW PACKET] ──► [Декодирование] ──► [Валидация GPS] ──► [Дедупликация] ──► [Обогащение IMEI] ──► [Публикация в Kafka]
  (TCP/HTTP/       (Бинарный /          (Проверка на         (Проверка по         (Поиск device_id      (Событие в топик)
   MQTT)            JSON)                GPS-drift)           timestamp/Redis)     в кеше)
```

### 3.2 Основные бизнес-сценарии (Use Cases)

**UC-1: Прием и нормализация потоковой телеметрии**
1.  Бортовое устройство отправляет пакет данных (одну или пакет из 100 накопившихся точек) по протоколу TCP/HTTP/MQTT.
2.  Сервис мгновенно возвращает протокольное подтверждение (ACK), предотвращая повторные отправки со стороны трекера.
3.  Пакет декодируется из бинарного формата/JSON в каноническую доменную модель TelemetryPoint.

**UC-2: Фильтрация аномалий и GPS-drift (Data Cleansing)**
1.  Сервис проверяет физическую валидность координат:
    *   Широта $[-90, 90]$, Долгота $[-180, 180]$.
    *   Нельзя переместиться на 500 км за 2 секунды (проверка скорости относительно предыдущей точки).
    *   Отсечение точек с количеством спутников $< 4$ или HDOP $> 5.0$.
2.  Валидные точки отправляются дальше по конвейеру, "мусорные" скидываются в лог аномалий.

**UC-3: Пакетная выгрузка из офлайн-буфера (Black Box Sync)**
1.  При выезде машины из зоны покрытия сети трекер копит точки в свою энергонезависимую память.
2.  При появлении связи трекер присылает пакет из 1,000+ накопившихся точек за прошлые сутки.
3.  Сервис корректно сортирует точки по их оригинальному timestamp (не по времени получения!) и передает в историю движения.

## 4. Функциональные требования (Functional Requirements)

*   **FR-1:** Сервис ДОЛЖЕН предоставлять Netty TCP-сервер и REST/MQTT эндпоинты для приема телеметрии.
*   **FR-2:** Сервис ДОЛЖЕН идентифицировать устройства по IMEI / Serial Number за $O(1)$ с использованием Redis.
*   **FR-3:** Сервис ДОЛЖЕН проводить валидацию координат и отбраковку некорректных GPS-данных.
*   **FR-4:** Сервис ДОЛЖЕН сохранять сырые данные в Time-Series хранилище (TimescaleDB) для построения исторических треков.
*   **FR-5:** Сервис ДОЛЖЕН асинхронно транслировать нормализованные события `TelemetryPointReceivedEvent` в брокер Kafka.
*   **FR-6:** Сервис ДОЛЖЕН поддерживать работу с мульти-точечными пакетами (Batch Ingestion).

## 5. Требования к качеству и SLA (Non-Functional Requirements)

*   **NFR-1 (High Throughput):** Пропускная способность сервиса — не менее 50,000 точек в секунду на один инстанс.
*   **NFR-2 (Low Latency):** Время обработки и подтверждения (ACK) одного пакета — не более 10 ms (p99).
*   **NFR-3 (Availability):** Высокая доступность 99.99% (схемы балансировки и горизонтального автомасштабирования).
*   **NFR-4 (Fault Tolerance):** В случае временного сбоя Kafka или БД сервис должен буферизировать входящие данные в локальную память/Netty ByteBuf без потери точек.
